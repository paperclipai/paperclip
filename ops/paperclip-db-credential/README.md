# Paperclip DB credential migration (review artifact)

This directory contains templates. **Do not install or run them on the live host before founder approval.** No live DSN, password, key, schedule or current host script is stored here.

## Trust boundary

- The Paperclip control plane runs as `paperclip-svc`. Its PostgreSQL URL is a systemd credential exposed only through `PAPERCLIP_DATABASE_URL_FILE`; `config.json` keeps `database.mode: "postgres"` but has no `database.connectionString`. Its adjacent `.env` has no `DATABASE_URL` or `DATABASE_MIGRATION_URL`. The service URL is never passed as a child environment value.
- An untrusted local CLI agent must have `filesystemScope: "workspace"`. With `PAPERCLIP_DATABASE_URL_FILE` set, the launcher rejects local runs without this scope, rejects DB/signing keys explicitly supplied to the agent environment, and the ACPX engine rejects local ACPX. Install Bubblewrap as a root-owned, non-writable regular executable at `/usr/bin/bwrap`, with root-owned, non-writable parent directories. Install the host SSH client with the same ownership and permissions at `/usr/bin/ssh` when using remote SSH agents. File-backed launches use these absolute paths without searching agent `PATH`; a custom `filesystemSandboxCommand` fails closed, and loader overrides such as `LD_PRELOAD` are stripped before host spawn. File-backed SSH ignores user SSH config so a `ProxyCommand` cannot start under the service UID; configure the remote host and key explicitly. Agent-authenticated issue and agent config mutations cannot set `filesystemSandboxCommand`. Verify `bwrap --help` lists `--bind-fd` before enabling local aliases; a Bubblewrap build without that option fails closed on launch. The bwrap mount planner rejects any workspace, executable, managed or extra mount that contains the service credential path. Writable workspace aliases use pinned directory descriptors and Bubblewrap `--bind-fd`, so a post-check path replacement cannot change the bound source. The bwrap mount and PID namespaces omit `/run/credentials`, the service config directory and host `/proc`. Reject any other `filesystemExtraPaths` or managed path that reintroduces service secrets. If bwrap or unprivileged user namespaces are unavailable, this local path fails closed; move that agent to an SSH environment under a different UID or to an isolated sandbox. An ACPX agent must run in an isolated sandbox or SSH environment under a different host UID. Other unconfined local adapters are **not eligible** for this deployment.
- The legacy `process` and `hermes_local` adapters start commands as the service UID without an isolation boundary. File-backed mode rejects their new selection, config updates and execution, including runs of existing agents on those adapters. Their environment checks fail before running a configured command. Inventory and migrate those agents to isolated adapters before cutover. The remote `hermes_gateway` adapter is a separate path.
- Treat a local agent's writable `CODEX_HOME` as untrusted input on every later remote/sandbox run. The service must stage allowlisted regular files through pinned, no-follow descriptors; accept a managed `auth.json` link only through its expected source chain; and stage only the selected, server-resolved skills. In file-backed mode, connector auth can come only from a server-owned home or private managed AI session, and agent API calls cannot change its source or digest. A link to a service credential, any directory symlink in a staged source path, or a replacement during staging must fail without copying bytes or including them in logs. A protected parent and service UID do not make a symlink trustworthy when the agent shares that UID; configure a direct canonical directory path instead of a volume alias. The `config.toml` preparation path must also avoid reading or writing through agent-planted links. File-backed staging requires POSIX descriptor support; ordinary Windows runs retain path-based staging without a service DB credential file.
- All agent-accessible workspaces, worktree `.paperclip/config.json`, `.env`, runtime homes and copied project trees must be scanned for the old URL before activation. Do not seed a worktree from the live PostgreSQL source after the migration. Host runtime services and shell bridges that can execute as `paperclip-svc` must be disabled or moved to an isolated runner before activation; a mount namespace around the main CLI alone cannot protect a host command launched by the service.
- Each host job runs as `pcjob-<instance>`, with its own URL and PostgreSQL role. The job credential source is distinct from the service credential. The six job scripts are installed root-owned with no inline DSN. An agent UID has neither the service nor job credential file in its namespace or permissions.

## Ordered live runbook — founder go required

1. Record SHA, approved PR, the exact six cron definitions and next occurrences, all agent dispatch/runners/host bridges and restart monitors, service status, old DB role and backup location. Confirm each rewritten job can run while the Paperclip service is stopped; if any cannot, resolve that dependency before cutover. Take an encrypted database backup and private copies of the seven original files; verify restore in a disposable environment. Keep the old URL for the negative check in a root-only file outside agent-readable homes and worktrees. Do not print it.
2. Stage separate OS users and a private `/etc/paperclip/credentials` tree. Install a reviewed Paperclip build root-owned and readable by `paperclip-svc` at `/opt/paperclip/app`, and stage the migrated instance data/config under `/var/lib/paperclip` with private ownership. Adjust absolute workspace/runtime paths for the new UID. Create a new service DB role and six separate job roles with unique generated passwords. Grant only required objects after reviewing each script's SQL. Restrict direct DB network access to service/job identities where the host firewall allows it. **Do not replace the live config, legacy scripts or cron entries yet.**
3. Stage rewritten copies of all seven carriers according to the map and `job-rewrite-templates.md` at private **new** paths. Stage the service drop-in for later activation; install the host job unit, `run-host-job`, `pg-client`, and six reviewed root-owned replacement scripts. Prepare root-owned replacement schedules that call `systemctl start paperclip-host-job@<instance>.service`, preserving exact schedules from the inventory, but leave them **disabled**. The six old scripts and their inline URLs remain at their original paths solely for their still-scheduled old cron occurrences; they are not copied into worktrees or the new deployment. Their containing home must remain inaccessible to any other agent UID. Do not rewrite or remove an old script while its old cron is still scheduled.
4. **Freeze before changing any live carrier.** Stop `paperclip.service`, every inventoried agent dispatch, runner, host runtime service, shell bridge and external restart monitor; drain/terminate existing agent processes, including detached ones. Verify `systemctl is-active paperclip.service` is nonzero, every inventoried launch path is stopped, and the agent PID inventory is empty. Keep this freeze throughout steps 5–7: no manual agent runs, restart automation, health probe that starts the service, or alternate host launch path may reopen dispatch. If any launch path cannot be stopped and verified, abort the cutover before touching old carriers. Old crons may continue during this freeze because they do not launch agents; their original files stay in place until each controlled cutover.
5. Cut over the six jobs **one at a time** at an inventoried schedule boundary while agent dispatch remains frozen: disable that old cron before its next occurrence, wait for its last invocation to exit, invoke the new unit exactly once for that occurrence and verify its expected DB action/exit code. If it fails, restore the old schedule or run the old occurrence once before the next deadline; do not enable the replacement. If it passes, enable the root-owned replacement schedule beginning with the **next** occurrence, retire the old entry, then move the old DSN-bearing script into the root-only rollback store and remove its original path. Confirm exactly one active schedule for that job before moving to the next. Record safe role names, exit codes, result counts and occurrence boundaries only. Do not print environment values in journal or diagnostics.
6. With all six old crons retired and no old invocation running, install the new service config and drop-in; remove the old inline URL from the legacy config, adjacent `.env`, cron definitions, worktree copies and any other inventoried carrier. Keep the service **stopped**. Verify every local adapter mount namespace policy and every ACPX/sandbox/remote target; reject unsafe host runtime definitions, extra mounts, references to the service home and worktree copies. Resolve any directory symlink in a staged `CODEX_HOME`, auth or selected-skill source path to a direct canonical directory before starting agents. Run the disposable Bubblewrap → remote `CODEX_HOME` leaf-link and same-UID `0700` parent-alias negative tests and bound auth/skills/JWT positive control from `paperclip-db-credential-server-e2e.sh` against the exact reviewed build; a failure blocks rollout. Run `verify-copies.py --old-url-file <private-old-url-file> --carrier <new-config> --carrier <each of six installed scripts> --carrier /opt/paperclip/app/.env --worktree-root <each agent worktree root>` from an operator shell; omit the application `.env` carrier only if it does not exist. It reports paths, modes and reason codes only. A missing/symlinked carrier, inline DB URL, worktree copy or **any** symlink in a scanned worktree fails; remove or replace symlinks before this gate. The root-only rollback store is excluded from agent mounts and remains offline.
7. **Pre-dispatch gate, while still frozen:** revoke the old DB role's `LOGIN`, rotate its password, terminate its existing sessions, and confirm by privileged SQL that `rolcanlogin = false` and zero sessions remain. Confirm all six replacement schedules active, all six old schedules absent, no old script at its original path, no agent PID, and all inventoried launch paths stopped. Run `python3 verify-old-url-revoked.py --old-url-file <private-old-url-file> --service-url-file <private-new-service-url-file>`; it must connect with the new service credential and fail to connect with the old URL, without putting either URL in argv or logs. The two private URL files must target the same host, port and database. Repeat the copy scan from step 6. **Any failed check keeps the service and agents stopped; no exception for a passing file scan alone.** Security performs an independent negative read/connect test.
8. Only after step 7 passes, start the new service and verify real Paperclip `/api/health` and a run-scoped JWT-authorized API request. Enable only the reviewed isolated agent targets, verify an agent cannot read the service/job credentials or connect with the old URL, and observe one replacement occurrence for each job. Recheck there is exactly one active schedule per job. Live service, role and cron changes in steps 2–8 all require founder go and DevOps execution.

## Rollback

If the service or a required job fails, freeze agent dispatch again before rollback and preserve logs without secret values. Before old-role revocation, restore a failed job's private original script and old cron only while the service remains stopped; keep exactly one scheduled occurrence. After revocation, prefer fixing the new role/grants and keep the old role disabled. If restoring the old role is unavoidable, keep the service and **all** agent launch paths stopped while restoring private config/scripts and schedules; do not restart the old service or permit agents until a new containment and credential-rotation gate is approved and verified. The founder must authorize any live credential reversal or rotation. Check `/api/health`, one JWT-authenticated call and every cron only after the applicable pre-dispatch gate passes. CI workflows and runs are outside this procedure.

## Synthetic proof

`scripts/smoke/paperclip-db-credential-e2e.sh` runs a disposable PostgreSQL container with one service role, six job roles, an initially active old role and separate OS UIDs. It proves that the pre-dispatch gate fails while the old URL still works, then revokes login, rotates the old password, terminates old sessions and proves the gate passes. It invokes each synthetic fixture through the installed `run-host-job` and proves success with its own grant and failure after revocation. It also checks that a clean worktree passes while a nested copy, an external-file symlink, and an external-directory symlink fail the scanner. It reports assertion counts only. `scripts/smoke/paperclip-db-credential-server-e2e.sh` boots the real API with a file-backed DB URL, completes a real `pg_dump`/`psql` round trip through a private libpq service file, and issues a run-scoped JWT. It checks a separate-UID Docker agent and Docker-backed remote sandbox transport, then runs the actual local `runAdapterExecutionTargetProcess` launcher with `filesystemScope: "workspace"` and inherited synthetic service DB/signing sources inside a disposable Bubblewrap container. The local agent proves the known credential path is absent, DB/signing environment keys are absent and its JWT API call succeeds; six unsafe local/ACPX launch attempts are rejected before agent launch. It plants both a leaf link from writable `CODEX_HOME/instructions.md` to the invisible synthetic service credential and a directory alias under a same-UID `0700` parent to an invisible synthetic service-only home. The subsequent host-side remote-home staging refuses both, removes each partial asset, and emits no credential bytes. A positive pass stages only the bound synthetic auth and selected skill while the run-scoped JWT API call still succeeds. A deterministic alias test replaces the canonical checked source with a symlink to the synthetic service directory before Bubblewrap starts and confirms the agent sees only the pinned safe directory. ACPX environment projection is checked by `packages/adapter-utils/src/acpx-engine/execute.test.ts`, including the inherited DB source and explicit run-scoped API token. The container tests prove the synthetic OS-file and DB-auth boundaries; the actual ACPX provider, live adapter mounts, host runtime services and real job SQL remain explicit rollout gates.

Both smoke Dockerfiles pin their base images by digest and their installed packages by exact version; each build verifies the package version. The nested Bubblewrap smoke needs `CAP_SYS_ADMIN` and unconfined seccomp/AppArmor on this Docker host, so it runs on a disposable internal bridge with only that capability, a read-only root filesystem and repository, and a writable non-secret workspace. Its credential file is a fixed synthetic value inside the image; no host credential fixture or Docker socket is mounted. The test asserts the container's effective capability mask before running the launcher. The real API remains loopback-bound and is reached through a short-lived bridge proxy; only the synthetic bridge address is allowlisted for this test. Do not reuse this container command with live credentials or a production service.
