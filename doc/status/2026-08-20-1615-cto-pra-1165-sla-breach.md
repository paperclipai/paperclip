## Summary

SLA monitoring fired at 15:31 UTC: https://travel.praesyn.com/ unreachable from
all monitoring regions (vps-1 + vps-2 blackbox exporters). Investigation
confirmed the site went down at ~15:28 UTC, was flapping until ~15:58 UTC, and
is now **UP and stable**. Root cause: the **auto-recovery script itself** —
concurrent `recover-travel-app.sh` invocations fought over the container,
causing a crash loop that kept travel_app down for ~30 minutes.

## Root Cause

**Primary: recovery-script concurrency race (TOCTOU).**

Both `/opt/travel_planner/scripts/recover-travel-app.sh` and
`/opt/scripts/voyonder-uptime.sh` used a PID-file latch with a classic
time-of-check-to-time-of-use race:

```bash
if [ -f "$PID_FILE" ]; then ... check kill -0 ... fi
echo "$$" > "$PID_FILE"     # not atomic with the check
```

Two instances starting within the same window both see no live PID, both write
their own PID, both proceed. During the incident the uptime monitor (cron,
every minute) invoked the recovery script while a forced `SKIP_HEALTH_CHECK=1`
recovery was already running → 4+ concurrent instances → `docker compose rm/up`
name conflicts → travel_app crash loop → ~30 min of 404/000 → all-region alert.

**Contributing:** the forced `SKIP_HEALTH_CHECK=1` invocation at 15:25:55 came
from an unknown trigger (no SSH session, no cron entry) — possibly a deploy
workflow or manual action. The health-check skip means recovery starts even if
the app is fine, and it ignores the "already healthy" fast-path.

## Fix Applied (durable hardening)

Replaced the racy PID-file latch with an **atomic `flock`** in both scripts on
vps-1 (`/usr/bin/flock` verified available):

1. **`/opt/travel_planner/scripts/recover-travel-app.sh`** — `exec 9>"$LOCK_FILE"; flock -n 9` — a second concurrent instance now exits immediately ("another instance is already running").
2. **`/opt/scripts/voyonder-uptime.sh`** — same flock-based lock (also fixes the monitor's own concurrent-cron race).
3. **Repo copy updated:** `scripts/uptime-monitor.sh` in the paperclip repo now matches (flock, same logic) so future deploys don't reintroduce the race.
4. Backups: `recover-travel-app.sh.pre-flock`, `recover-travel-app.sh.bak` retained on vps-1.
5. Both scripts syntax-checked (`bash -n`) on host before and after install.

Note: a previous edit at 15:58 (recover-travel-app.sh.bak diff) had refactored
the container-state checks but did NOT fix the lock race — that was the actual
bug.
