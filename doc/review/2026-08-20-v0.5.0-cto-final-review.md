### 1. Billing (743-line service, 247-line routes, 7 tests)

**Strengths:**
- Webhook route (`/webhook`) correctly mounted BEFORE auth middleware — raw body needed for Stripe signature verification ✓
- All mutation endpoints (POST/PATCH subscription, cancel, reactivate, report usage, sync invoices) use `requireBoardUser` = `assertBoard` + `req.actor.userId` ✓
- All endpoints use `assertCompanyAccess` for company-scoping ✓
- Stripe webhook signature verification via `stripe.webhooks.constructEvent()` ✓
- Comprehensive webhook handling: invoice.paid, invoice.payment_failed, customer.subscription.updated, customer.subscription.deleted ✓
- Fire-and-forget notification dispatch on payment failure (`.catch` guarded) ✓
- Idempotent invoice upsert (checks existing stripeInvoiceId) ✓
- Usage reporting with overage calculation and Stripe usage record submission ✓
- Proper error types: `notFound`, `unprocessable`, `badRequest` ✓

**Advisory:**
1. Billing GET routes (tiers, subscription, usage, invoices, overview) use `assertCompanyAccess` which permits agent readers. If billing data is sensitive, consider requiring `assertBoard` on these too. Low risk — agents in the company already see budget data.
2. In `getOrCreateStripeCustomer`, the returned `{ id, stripeCustomerId }` destructured as `const { id: stripeCustomerId }` in `createOrUpdateSubscription` is semantically confusing: the variable name suggests the Stripe customer ID, but `id` is the DB record ID. It works correctly since the downstream query uses the DB record ID, but a rename to clarify would improve readability.
