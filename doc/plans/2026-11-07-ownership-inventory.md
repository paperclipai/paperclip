## Summary

The control plane has **83 distinct durable in-progress record kinds**, in 94 inventory rows. 11 rows describe storage that another subsystem already owns. They are merged below and kept in the appendix as cross-references.

| Obligation | Kinds |

Every kind has a row in the index below. The full columns (writer, in-progress states, owner, release rule, proof) are in the appendix tables. The lists under "Cross-subsystem overlaps" name the kinds whose release today depends on age, or that nothing releases at all.

The five findings that matter most for Phase 1:

1. **"Owner gone" is decided by at least 31 separate signal-0 sites and 3 boot ids, and the proofs disagree.** One process mints three boot UUIDs (`controller-process-identity.ts:13`, `native-restart-recovery.ts:284`, `legacy-controller-lease.ts:8`). The rules contradict each other:
   - On EPERM: `heartbeat/recovery.ts:308` treats the pid as alive; `local-service-supervisor.ts:245` treats it as dead.
   - On pid reuse: `native-failed-run-owner-release.ts:97,113` and `native-session-executor.ts:592` count any 1 ms start-time difference as a reused pid. `ps lstart` has 1 s precision, so on macOS they can release a live owner. `native-restart-recovery.ts:348-358` and `controller-process-identity.ts:90` need a gap of at least 1 s.

   Section A must pick one stamp and one prover.
2. **Three proofs accept "the pid is dead here" as proof that an owner on another host is gone.** This breaks the plan's rule that a different host is never proof:
   - `evaluateNativeControllerTakeover` (`native-restart-recovery.ts:360-437`); `native_run_finalizations` has no host column;
   - the runtime-control sweep (`workspace-operations.ts:126-135`);
   - the orphan reaper `terminalizeOrphanedRunningRun` (`recovery/service.ts:6096`).

   Three of the ten proofs check the host:
   - `controllerProcessExited` (`controller-process-identity.ts:83-91`) compares a host, boot and pid-namespace hash. On another host it returns "not exited", and the record waits out a TTL (15 or 30 min).
   - `proveLocalWorkspaceOwnerStopped` (`native-workspace-owner-stop-proof.ts:62-106`) returns `unsupported` / `foreign_host`. That is the closest existing equivalent of `unprovable`.
   - `recordedLocalExecutionStopped` (`native-local-process-stop.ts:27-40`) requires the recorded hostname.

   No shared prover returns `unprovable`, and only `controllerProcessExited` also checks the boot id and the pid namespace.
3. **Company-wide admission still waits on cleanup and accounting through five gates** (invariant 3, section D):
   - `waitingRunCount` (`budget-exposure.ts:201-202`);
   - `recoveringRunCount` (`budgets.ts:858`);
   - the scope budget hold (`budgets.ts:860`);
   - the 15 s `budget_evaluation_work` gate (`budgets.ts:863-872`);
   - the per-issue `hasPendingRunCleanup` successor block (`heartbeat/queue.ts:1129`, `execution-blocker.ts:70-102`), which fails closed when the run row is missing.

   A run with `accountingCaptureFailed=true` is skipped by accounting (`run-cost-accounting.ts:250,389`). It is not "recovering" either (`budget-exposure.ts:140-146`), so it holds `waitingRunCount` until the UTC month rolls over.
4. **Several records have no automatic release, so a crash leaves a permanent hold with no next action** (invariants 2 and 7):
   - `remote_workspace_provision` rows left `running`/`uncertain` (`remote-workspaces.ts:973-990`). They block every later reservation of that workspace.
   - The runtime skill-cache lock (`runtime-skill-cache.ts:134-140`). It is on the turn path: the next run waits 60 s, then fails.
   - Unpriced service-invocation reservations (`decision-models.ts:217`, `prompt-injection-prevention.ts:178`, `fast-responses.ts:691`).
   - Create intents on providers other than Daytona: only Daytona declares `creationOperationVersion: 1` (`daytona/src/manifest.ts:42`), so a crashed create elsewhere ends in operator reconciliation.
   - The same-boot legacy settlement receipt (`legacy-process-settlement.ts:68,98`). Without it, instance sleep stays blocked (`idle-retry-schedule.ts:100-132`).
5. **Restarts still spend the work budget, and the per-restart guard is dead code** (invariant 5, section F):
   - `processLossRetryCount` has no writer and is read only at `heartbeat/recovery.ts:2675`, so its guard always passes.
   - Interrupted preparation, where no provider work started, charges the same `failureRetries` counter as real failures (`execution-recovery-attempt.ts:61-67`).
   - "Provider work started" has five independent proofs (four in accounting, plus the Runner's `startup_attempt.before_spawn`). Section F should collapse them onto the B outcome records.

## Definitions used by every row

- **In-progress state:** a non-terminal value that a live process is expected to move forward.
- **Owner recorded:** the identity stored on the record that may move it, such as a boot id, pid, lease token, run id or fence token. "none" means the record stores no owner.
- **Proof:** the code that decides that the owner is gone or that the record is safe to release. Age-based proofs are marked TTL/age.
- **Obligation:** exactly one of ownership, accepted result, workspace preservation, or accounting (plan, "Relationship to the zero-downtime upgrade work", item 3). Readers labelled work-intent delivery as ownership (it moves to E), and the attempt budget as ownership (it moves to F).

- **`native_run_finalizations.lease_owner`: 8 or more release paths.** Executor settlement (native-session-executor.ts:11378, 11521), `releaseUnstartedNativeExecutionClaim` (native-execution-lease.ts:58), `settleFailedRunOwner` (native-failed-run-owner-release.ts:170), `releaseDeadControllerResultLeases` (native-dead-controller-result-lease.ts:82), the restart takeover (native-restart-recovery.ts:1514), the resume claim (native-finalization-reconciler.ts:299), checkpoint-failure expiry (native-runner-checkpoint.ts:165), and the finalizer (native-run-finalizer.ts:240, 451). Restart recovery and the periodic loop also both call `reconcileNativeFinalizations` (heartbeat/recovery.ts:956, 2836).
- **An `active` environment lease: 4 release paths.** `releaseRunLeases` (environment-run-orchestrator.ts:326, 796), native settlement (native-environment-settlement-work.ts:50-75), the reaper orphan flip (heartbeat/recovery.ts:2894), and live-recovery `orphanLease` (heartbeat/recovery.ts:2960).
- **A `pending_cleanup` teardown: 3 claimers, 2 renewal loops.** The stop-only claim (environment-runtime.ts:3951) does not renew its 15 min fence.
- **A `running` run with a dead process: 2 reapers with different outcomes.** `recoverActiveExecutions` (heartbeat/recovery.ts:2374) sets `failed/process_lost` and can retry. `terminalizeOrphanedRunningRun` (recovery/service.ts:6096) sets `interrupted` and never retries. Whichever runs first decides whether a retry happens.
- **A `workspace_finalize` operation: 3 release paths.** #19807 supersession (native-workspace-finalization-supersession.ts:21-91), offline reconciliation (offline-workspace-operation-reconciliation.ts:30-118), and `reconcileOnlineWorkspaceOperations` (:152), which has no production caller.
- **The issue execution lock: about 10 clear sites.** These are the wake-queue release (wake-queue postgres.ts:1255), about 8 inline clears in heartbeat/queue.ts, `sweepStaleIssueLocks`, and the checkout release. Each one decides on its own terms that the run is terminal.
- **Deferred-wake promotion: 2 loops.** The release drain (use-cases.ts:135) and deferred-receipt work (deferred-receipt-work.ts:16, every 30 s). Only a CAS (postgres.ts:497) reconciles them.
- **The legacy shutdown fence.** Both the owner and the sweep release it. After a boot-id mismatch, the sweep still waits for the deadline.

### Local-disk records that conflict with an ephemeral filesystem

These records live on a local disk. A replacement host loses them, and neither `ephemeral-server-contract.ts` nor `heartbeat/upgrade-readiness.ts` lists them:
- the usage-receipt spool (`idle-local-work.ts:18`);
- the sandbox orphan-cleanup spool (`idle-local-work.ts:19-20`);
- the runtime skill-cache lock (`runtime-skill-cache.ts:116-140`).

Also, `upgrade-readiness.ts:53-61` reads only `active` runner-task leases. It ignores in-flight `pending_cleanup` claims and `pending` create intents, so a replacement server inherits them on the 15 and 30 min TTLs.

#### 1b. Terminal wake outcomes and temporary refusals

"T" means the refusal can be temporary. Each of these writes a terminal row (`skipped`, `cancelled` or `failed`) with no promotion path. A durable caller receipt (`executionWaitRequestId`) is the exception: it is kept as `deferred_issue_execution` (q:2452-2459).

- `heartbeat.scheduling_suppressed` (q:2527). **T**: a DB restore or worktree mode ends. Task drain is exempt (q:2524).
- `company.inactive` (q:2550). **T** if the company is paused. A user request gets a 409 instead.
- `budget.blocked` (q:2732). The skip row is written at admission for any budget block. The claim path treats only a board-owned block as terminal (q:917). Admission does not make that distinction. **T** for accounting-settling holds.
- `agent.not_invokable` (q:2747). **T** for paused or `pending_approval`. Setup is exempt (q:2744).
- `heartbeat.disabled` / `heartbeat.wakeOnDemand.disabled` (q:2761/2765). Configuration.
- `heartbeat.timer.no_actionable_work` (q:2774). Not work.
- `heartbeat.worktree_execution_cutoff` (q:2649, q:3465). Configuration.
- `issue_tree_hold_active` (q:2799). **T**. The tree-resume path only revisits *cancelled runs* (issue-tree-resume.ts:171-199), not skipped admission wakes. Another re-wake path is **unverified**.
- `issue_dependencies_blocked` (q:3817 via execution-wait.ts:14). **T**. Covered by the separate dependency backstop rs:5782, which re-wakes rather than promoting this row.
- `execution_reconciliation_required` (q:3384 else branch, recordExecutionWait). **T**.
- `issue_rewake_throttled` (q:4224). **T**.
- Daily cap (q:4265, q:4674). Claim-time path q:437 → run `cancelled`, wake `skipped`. **T**: resets daily.
- Chat-control recovery `unresolved` (q:3001 admission; q:695-760 dispatch → run `failed` + wake `failed`). **T**: the code is `CHAT_CONTROL_RECOVERY_UNRESOLVED_CODE`, meaning the stop proof is not yet available. At claim it returns null and stays queued (q:695). At admission and dispatch it is terminal.
- Issue missing or state-guard mismatch (q:3149, q:3211), native-status target gone/reassigned (q:4965), worktree needs project code (q:3949). Task changed, so these are legitimately terminal.
