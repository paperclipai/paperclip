## 1. What the paper is

A 71-page systematic survey establishing the **agent execution harness** — the infrastructure wrapping the model — as an independent engineering surface, with three contributions:

1. **Conceptual framework**: harness engineering as the third stage of a widening scope: prompt engineering (optimize one model call) → context engineering (optimize what the model sees each step) → harness engineering (optimize how the whole closed-loop system runs). The harness "determines how model outputs become actions, how environmental outcomes return as feedback, when execution continues or stops, and which operations require constraints or human approval."
2. **ETCLOVG**, a seven-layer taxonomy: **E**xecution environment, **T**ool interface, **C**ontext management, **L**ifecycle/Orchestration, **O**bservability, **V**erification, **G**overnance. E/T/C/L are the *structural pillars* (what the agent can do); O/V/G are the *control plane* (how confidently/safely it operates). It extends Meng et al.'s six-component harness model by promoting Observability and Governance to first-class layers and folding state management into Lifecycle.
3. **Ecosystem map**: 170+ open-source projects coded onto the taxonomy (snapshot frozen 2026-05-08). Findings: E/T/L/V are densely covered; C is usually embedded in frameworks rather than standalone; **O and G are the thinnest layers in open source** — operational control matured later than runtime/benchmark infrastructure.

The central thesis ("binding constraint"): *task execution reliability depends less on the underlying model than on the harness*, and measured agent performance is a property of the **model–harness pair**, never the model alone.

## 2. Layer-by-layer technical findings (the specifics worth keeping)

### E — Execution environment & sandbox (§3)

- Sandboxing serves **three purposes**, and the third is new to the agent era:
  1. **Security** — LLM-generated code is unauditable at scale; prompt injection turns a benign agent into an attack vector.
  2. **Reproducibility** — cheap reset-to-baseline is what makes SWE-bench/OSWorld-style evaluation and RL-style training practical; "the absence of a cheap reset mechanism is itself a scalability bottleneck."
  3. **Liveness** — without a sandbox every risky action needs a human permission prompt; at scale users either abandon the agent or approve reflexively. A sandbox is "simultaneously a cage and a license": it converts permission from a per-action question into a session configuration. **Anthropic: sandboxing Claude Code cut permission prompts by 84%** while preserving safety.
- Seven sandbox categories: general-purpose managed (E2B/Modal/Daytona/Docker Sandboxes — trending from shared-kernel containers to dedicated-kernel microVMs), computer-use (full desktop, heaviest), code-specialized (Judge0, WASM/Pyodide — trending container→WebAssembly for capability security + microsecond instantiation), framework-integrated (OpenHands — "bundle vs compose" tradeoff), browser eval environments, **OS-level permission sandboxes** (bubblewrap/Seatbelt allowlists — "permission, not partition"; right when the threat is prompt-injection, not fully adversarial code), and **sandbox abstraction layers** (SWE-ReX, smolagents executors, Kubernetes Sandbox CRD — make the substrate replaceable so orchestration logic isn't coupled to one vendor).
- Threat data: **SandboxEscapeBench reports 15–35% escape success rates for frontier models against Docker containers** depending on configuration. Defenses are immature: IsolateGPT (<30% overhead for 75% of queries), transactional sandboxing (~14.5% overhead, rollback-based).
- Deployment modes: self-hosted (lowest latency, full ops burden), SaaS, hybrid/BYOC — chosen along latency/security/scalability plus compliance/data-residency.

### T — Tool interface & protocol (§4)

- The layer sits on a fault line: **capability coverage (more tools) vs decision quality (small action space, small prompt footprint)**. Production guidance repeatedly reports oversized tool menus degrade reliability and amplify planning errors.
- Organize standards by the **integration boundary they cross**, not vendor: Model↔Function (function calling), Agent↔Capability (MCP, OpenAPI), Agent↔Agent (A2A/ACP/ANP — the only row with first-class long-running support), Agent↔Repo (AGENTS.md — convention-level).
- Two design principles with empirical backing: (1) **"fewer but better tools"** outperforms brute-force exposure (shrinks prompt entropy and planner branching); (2) **discovery must be adaptive** — static global tool lists don't scale; retrieval-aware tool/skill selection (MCP-Zero, ToolRet, SkillRouter/SkillRet) is a first-order determinant of downstream success.
- Verification-adjacent tools (analyzers, solvers, checkers) should return **evidence-bearing artifacts** (traces, counterexamples, structured certificates), not black-box yes/no.
- Session management failure modes: stale handles, inconsistent tool state across retries, context saturation from verbose tool traces → need explicit tool-session lifecycles, bounded tool-context injection, and observability hooks that attribute errors to planner vs interface.

### C — Context & memory (§5)

- Why context must be engineered: attention is quadratic (window = scarce resource); **U-shaped attention curve** (Liu et al.: >30% accuracy drop when the relevant document sits mid-context vs edges, robust across models); **context rot** (Hong et al., 18 frontier models: every model degrades as input grows, degradation starts well before the window is full — a 200K-rated model can lose significantly at 50K; semantically ambiguous queries degrade fastest).
- Guiding principle: *smallest set of high-signal tokens that maximizes the probability of the desired outcome at each step.*
- Three memory tiers (maps to OS memory hierarchy):
  - **Short-term (active window)**: system-prompt "altitude" calibration (start minimal, add instructions only against observed failures); token-efficient tool design; **progressive disclosure / just-in-time retrieval** (keep lightweight identifiers — paths, queries, links — and load on demand; Claude Code's CLAUDE.md-at-start + glob/grep-on-demand hybrid); **KV-cache-aware design** — Manus: cache hit rate is "the single most important metric for a production-stage AI agent" (cached $0.30/MTok vs $3.00 uncached on Sonnet). Three rules: stable prompt prefix (one token invalidates everything after), append-only context (never mutate past actions), deterministic serialization (**non-stable JSON key ordering silently invalidates caches**). Don't add/remove tool definitions mid-session; mask logits instead.
  - **Mid-term (session/cross-run)**: structured note-taking (NOTES.md/todo.md read at start, updated before reset — the Claude-plays-Pokémon result), file-based planning, cross-run injection (capture last run's salient output, prepend to next). "A few hundred tokens of structured working state can bridge context resets that would otherwise lose all progress."
  - **Long-term (indexed store)**: MemGPT (context=RAM, storage=disk, explicit paging); Generative Agents' **observation–reflection–retrieval triad** (recency+importance+relevance scoring; each component independently load-bearing in ablation); MemoryBank (Ebbinghaus decay, access strengthens, contradiction resolution); Mem0 (vector+graph+KV hybrid; 26% higher accuracy than OpenAI native memory at 90% fewer tokens vs full-context); A-MEM (Zettelkasten: new memories retroactively update links of old ones); **cq/Mozilla (collective memory: org-shared knowledge across a fleet, with a post-error hook that queries collective knowledge on failure — prevents N agents independently rediscovering the same fix)**.
- **Long-horizon (100+ turns)**: compaction (tune recall-first then precision — over-pruning is unrecoverable); tool-result clearing (replace consumed outputs with path references) as the lightest continuous compaction; **sub-agent context isolation** (subtasks explore in fresh windows, return 1,000–2,000-token distilled summaries; share full context only when genuinely needed — sharing kills KV-cache reuse); hybrid decision framework: pre-load always-needed, retrieve conditionally-needed, compact near saturation, spawn sub-agents for polluting exploration. Key line: **"Context management should be the infrastructure's job, not the agent's."**
- **Context drift ≠ context rot**: rot is per-inference degradation; drift is trajectory-level divergence — after 100+ turns agents repeat done work, contradict earlier decisions, lose the motivating goal; compaction summaries carry compounding inaccuracies; a drifting agent doesn't know what to retrieve to correct course. Conclusion: context engineering alone cannot solve long-horizon reliability — you need verification loops, HITL checkpoints, and behavioral anomaly detection (i.e., the O/V/G layers).

### L — Lifecycle & orchestration (§6)

- Three organization levels: single-agent inner loop (ReAct-style), multi-agent patterns (hierarchical / team / workflow / fan-out / graph composition), and the **full lifecycle pipeline from issue to pull request**.
- State axis: stateless replay (reconstruct from history; auditable, costly at scale — Codex CLI) vs stateful (files/DB/task graphs; continuous, recovery-friendly, harder to debug) vs hybrid (most practical systems).
- The **task runner** is the central full-lifecycle abstraction: "a harness that manages scheduling, state persistence, retries, validation, and iterative refinement over a complete task lifecycle," grounded in persistent artifacts (repos, issues, branches, tests, PRs), where "humans steer while agents execute." Named systems in this category: **Vibe Kanban, OpenAI Symphony, GitHub Agentic Workflows** — this is Paperclip's exact category (see §5 below).
- Anthropic's four recurring failure modes of long-running coding agents: (1) tries to one-shot the whole task, (2) declares completion prematurely, (3) leaves the environment broken between sessions, (4) marks features done without testing. Their fix is harness-side, not model-side: an **initializer agent** that decomposes into a feature list and sets up progress artifacts (git repo, progress file, init script), then a coding agent working **one feature at a time with clean handoff state**.
- **Managed Agents architecture** (Anthropic 2026e): decouple the **brain** (harness+LLM) from the **hands** (sandboxes/tools) and the **session** (durable event log). Each independently recoverable: harness crash → reboot new instance with `wake(sessionId)`, resume from last event; sandbox death → caught as tool-call failure, reprovision; **credentials live in an external vault and never enter the sandbox**. Pets → cattle as the prerequisite for fleet-scale reliability.

### O — Observability & operations (§7)

- Foundation: structured trace trees (every LLM call, tool call, retrieval, context-assembly op as spans). **OpenTelemetry GenAI semantic conventions** are the de facto standard (OpenLLMetry, OpenInference) — lets agent traces flow into existing Prometheus/Grafana/Datadog stacks.
- Agent-specific layers add: session/agent/task/workflow/tool/LLM **hierarchical span models** (AgentOps), **cognitive observability** (Watson: a surrogate agent reproduces the primary agent's output while emitting a reasoning trace — usable for debugging and automated correction), eBPF-based out-of-process monitoring (AgentSight, <3% overhead, can't be bypassed by a compromised agent), and task-flow discovery. Survey stat: **79% of practitioners name non-deterministic execution flow as the top challenge** in agentic systems.
- Cost: track (per-call and per-task attribution) and optimize (FrugalGPT cascading — up to 98% cost reduction matching GPT-4 quality; semantic caching; token-budget routing; **TALE's token elasticity: setting the reasoning budget too low paradoxically increases token spend**). **Infrastructure noise alone shifts agentic benchmark scores by 6 points (p<0.01)** — cost cuts silently degrade quality unless observability is fine-grained.
- Reliability: layered failure taxonomies. MAST: 14 multi-agent failure modes in 3 clusters (system design, inter-agent misalignment, task verification; κ=0.88). AgentErrorTaxonomy: failures by module, with **error propagation (one root cause cascading through later decisions) as the central bottleneck**; root-cause-isolating debugging (AgentDebug) yields up to **26% relative task-success improvement**. AgentFixer on IBM's production system: 15 validators detect 64–88% of issues, and **38% of task failures trace to parsing errors — fully addressable by deterministic checks**. QSAF: hallucinated outputs stored into persistent memory create **self-reinforcing degradation loops across sessions**.
- Detection strategy: **rule-based checks for structural failures (cheap, inline) → statistical monitoring for drift → LLM-based semantic analysis for reasoning failures (async)**.
- **The harness-as-assumption principle**: "every harness component encodes an assumption about what the model cannot do on its own, and those assumptions go stale as models improve." Concrete: upgrading Opus 4.5→4.6, Anthropic **removed the sprint construct and context resets entirely, cutting cost from $200 to $125 with no quality loss**. The ideal observability stack has a meta-monitoring layer tracking which interventions are still load-bearing, enabling continuous harness *simplification*.
- The observability–evaluation gap: **89% of teams run observability, only 52.4% run offline evals** (LangChain survey) — teams see what agents did without judging whether it was correct. Fix: production traces auto-become regression tests; eval scores become alerting signals.

### V — Verification & evaluation (§8)

- Core reframe: a benchmark score is a property of the **model–harness pair**; evaluation is a five-stage **task-to-feedback lifecycle**, not a terminal scoring step:
  1. **Task & benchmark grounding** — a task is an embedded problem: environment state + tools + allowed actions + constraints + termination conditions + success criteria. "Strong outcome verifiers require strong task grounding."
  2. **Pre-execution readiness validation** — before the agent runs, validate sandbox/deps/tools/context-reset/permissions/budgets/graders. Otherwise "evaluation infrastructure noise masquerades as model failure": broken tools, stale context, non-reset sandboxes, flaky tests, unstable judges. Record the full harness configuration (tool registry, context policy, permission policy, budget, timeout, model config) as evaluation metadata.
  3. **Controlled execution & trace capture** — the rollout (task + model config + harness config + action sequence + observations + final state + grade) is the unit; fix accidental variation; repeated rollouts expose variance instead of hiding it. Traces are **primary evaluation data**, not debug artifacts.
  4. **Multi-level judgement & failure attribution** — judge at three levels: outcome (did it work), **trajectory** (right tools, sensible ordering, no redundant calls, permissions respected, recovery worked — a correct answer with an unacceptable path is still a failure), and **evaluator** (is the grader itself trustworthy — flaky tests and biased LLM judges misattribute noise to the agent; "the evaluator should be treated as a component under test, not as an oracle"). Attribution maps trajectory signals to layers: wrong tool → T; forgot constraint → C; unrecovered loop → L.
  5. **Continuous regression & deployment feedback** — regression triggered by **harness changes, not just model changes** (tool descriptions, compaction policies, sandbox images, permission rules, judge prompts all alter behavior; local improvements create global regressions). Layered suite: unit-like tool-schema tests → single-step decision tests → full-rollout tests → multi-turn simulations. Production traces convert into regression cases.
- Cost-aware evaluation: expose a **success–cost–latency frontier**, not a success-rate leaderboard.
- Frontier direction: Meta-Harness — the harness itself as an object of automated search; evaluation becomes the signal that improves the harness.

### G — Governance & security (§9)

- Permission models along a **granularity axis**: static boundaries (allow/deny lists — inspectable but can't express task intent) → **contextual per-call policies** (Progent's DSL over tool names/args/environment; Conseca: LLM *generates* a task-specific policy from trusted context, a separate **deterministic checker enforces it** — generation adapts, enforcement stays auditable) → cross-boundary (authenticated delegation: OAuth/OIDC extended with User ID / Agent ID / scoped Delegation tokens forming a verifiable accountability chain from human principal to agent action; agent-permissions.json as robots.txt-for-agents).
- **Credential pattern** (Skyvern): secrets in a vault, only placeholders in LLM context, raw values substituted at the execution layer. Open problem: mid-trajectory token expiry/renewal while keeping credentials out of context.
- **Lifecycle hooks** — four canonical points per tool-use cycle: H1 input guardrails (pre-LLM), H2 action validation (pre-tool), H3 information-flow control on tool output (post-exec, taint tracking à la CaMeL: untrusted data cannot influence control flow), H4 human-in-the-loop for consequential actions. Hook-stacking interactions are unstudied (an upstream sanitizer can weaken a downstream detector).
- **Approval habituation is empirically real**: Felt et al. — only 17% of users attend to permission dialogs, 3% comprehend them. "Frequent requests lead users to approve dangerous actions reflexively, while infrequent requests leave coverage gaps." Design dimensions: validation scope, alert richness, recurrence policy (allow-once vs allow-always).
- **Declarative constitutions**: externalize governance into versioned, diffable config (YAML) rather than code — pipeline tier, risk patterns, tool allow/deny, token budgets, audit destinations; reviewable by non-developers; contrasted with training-time constitutions (hard to modify, probabilistic). Middle point: programmable policy DSLs (Progent; Formal-LLM's pushdown-automata plan constraints — can express ordering constraints, prohibited tool combos, required approval gates at specific steps).
- **Audit infrastructure**: per-tool-call JSONL with tool, args, risk class, permission decision + policy version, result, token cost, latency; a replayable record needs trace id, principal identity, and an **integrity hash — few systems sign records, leaving audit trails tamperable by a compromised agent process**. Anomaly detection splits per-action (inline, cheap, misses distributed attacks) vs trajectory-level (async over the audit log, catches slow multi-step attacks). Cost governance: OWASP lists resource drain as a distinct LLM risk; fan-out multiplies API calls exponentially.
- Landscape: across six surveyed production agents (Codex, Gemini CLI, OpenHands, Browser Use, Nanobrowser, Skyvern), **information flow control, identity management, and formal verification are absent from every one**, and monitoring is partial everywhere. Supply chain: open-source models hallucinate nonexistent package names at 21.7% ("slopsquatting" registration attacks).

### Cross-layer synthesis (§10–12)

- **Cost–quality–speed trilemma**: stronger V/G/O/E all cost latency and money; systems must choose which checks are synchronous vs offline vs regression-only.
- **Capability–control tradeoff**: every authority increase (bigger tool menus, persistent memory, permissive sandboxes) expands selection error, injection surface, provenance/staleness risk, blast radius.
- **Harness coupling problem**: layers interact (tool descriptions consume context budget; execution environment changes eval results; traces are governance evidence only if identity/permissions captured at the same granularity) → **harness changes must be tested as system changes**; a component that helps in isolation can degrade the composed rollout.
- **Frameworks → platforms**: "platforms add durable workspaces, managed sandboxes, identity, billing, observability, evaluation, governance, and human handoff across many runs and users... fleets of agents whose actions remain inspectable and reversible over time."
- Five open problems: (12.1) hardened/scalable execution substrates with cost models for choosing isolation primitives; (12.2) **context management recast as state estimation** — bound divergence between agent's internal state and true task state; provenance for remembered facts, staleness markers, contradiction handling, reconstruction from durable artifacts; (12.3) **trace-native failure diagnosis** (close the 89%/52% observability–evaluation gap); (12.4) **standard handoff contracts** — a handoff (planner→executor, agent→tool, subagent→parent, system→human) should carry: *intent, constraints, permissions, artifacts, provenance, budget state, risk level, trace history, unresolved decisions* — plus explicit responsibility (who authorized, what transferred, what evidence, what the receiver may do, when control returns); (12.5) **keeping harnesses useful as models improve** — factorial model×harness evaluation; shadow/A-B tests across harness variants; adaptive simplification.

## 3. Where Paperclip sits (mapping + validation)

Paperclip is, in the paper's vocabulary, an **agent platform** (§11.4) built around a **full-lifecycle task runner** (§6.4) — the same category as Vibe Kanban, OpenAI Symphony, and GitHub Agentic Workflows. The paper explicitly notes "OpenAI's Symphony frames the issue tracker and repository as a control plane for agent work" — which is Paperclip's founding thesis. That is strong independent validation, and it also names our direct competitive cohort.

Layer-by-layer, what we already have vs where the paper says the ecosystem (and we) are thin:

| Layer | Paperclip today | Assessment vs paper |
|---|---|---|
| E | Per-issue git worktrees, sandbox bridge (confined syncIn), workspace provisioning with DB seeds, runtime services | Solid mid-tier. No pluggable isolation backends (abstraction layer), no cheap reset-to-baseline replay, threat model implicit |
| T | MCP delivery = permitted ∩ installed, skills catalog with trust levels + content hashes, ToolSearch-style deferred tools, AGENTS.md per agent | Strong. Deferred-tool loading is exactly the paper's "retrieval-aware tool selection"; skill hashing anticipates ETDI-style signed tool definitions |
| C | heartbeat-context endpoint, continuation summaries, wake payloads, agent memory files (MEMORY.md index + per-fact files) | Good mid-term tier. Long-term tier is per-agent only (no collective memory); no KV-cache-aware prompt assembly discipline in adapters; compaction is adapter-internal, unobserved |
| L | Checkout/heartbeats, first-class blockers with `issue_blockers_resolved` wakes, children-completed wakes, watchdogs, recovery actions, execution policies with staged review, monitor scheduling | This is our deepest layer — matches the paper's task-runner spec nearly point-for-point (scheduling, state persistence, retries, validation, refinement) |
| O | Runs, transcripts, per-run cost/budget tracking, productivity reviews, watchdog notes, and opt-in OpenTelemetry traces for server requests plus task/startup/sandbox/turn execution | Still thin relative to the paper. Existing spans do not yet provide complete GenAI-semantic coverage of every model call, tool call, retrieval, and context-assembly operation; there is also no failure taxonomy over runs, trajectory-level anomaly detection, or meta-monitoring of harness features |
| V | Done-gates, QA handoff issues, greploop, Greptile check-run verdicts, evals follow-ups | Partial. No pre-execution readiness stage (see below), no harness-change-triggered regression suite, no trace-native attribution, no evaluator-under-test versioning |
| G | Run-JWTs scoped to checked-out issue (1h expiry), assignment-based PATCH authorization, MCP ask-first approval gates (approve-and-run-once semantics), board approvals for spend, typed interactions, X-Paperclip-Run-Id audit header, budget gates (80% → critical-only) | Strong relative to the surveyed field (most production agents have *no* identity management; we do). Gaps: no declarative policy constitution, audit records unsigned, no taint tracking on tool outputs, delegation chain not formalized as tokens |

A concrete example from the research run: workspace setup failed while its database restore reported "database system is shutting down; write EPIPE". That is *precisely* the paper's Stage-2 finding: **infrastructure noise masquerading as agent failure**. Paperclip already classifies `setup_failed` distinctly and has bounded retry lanes for transient upstream failures, workspace contention, and selected interaction-continuation infrastructure failures. What remains missing is one unified pre-dispatch readiness stage with explicit per-check results, consistent retry eligibility, and aggregation that shows what fraction of failed runs are harness failures.

## 4. Lessons to borrow — point-by-point technical proposals

Ordered by expected value; each is scoped as a borrowable mechanism with the paper's evidence attached.

### P1 — Pre-execution readiness validation as a first-class run stage (V, Stage 2)
Before the adapter is invoked: verify worktree provision, DB seed restore, tool/MCP availability, credential validity, and budget headroom as a **readiness checklist with per-check results recorded on the run**. Extend the existing bounded retry scheduler so each readiness failure has an explicit retry policy and a specific code such as `setup_failed:<check>`; this separates harness noise from agent failures without duplicating current retry machinery. Paper evidence: infra noise shifts scores 6pp (p<0.01); flaky setup makes failure attribution impossible. Extension: persist the harness configuration snapshot (skills roster + hashes, model, tool registry, permission policy, budget) as run metadata — the paper's "record the measurement instrument" requirement, which also enables factorial model×harness analysis later (P8).

### P2 — Standard handoff contract schema (§12.4) for continuation summaries, wakes, and delegation
Our continuation summaries are prose. Adopt the paper's field list as a typed schema carried by: run→run continuations, parent→child issue delegation, agent→agent reassignment, and agent→human escalation: `{intent, constraints, permissions, artifacts, provenance, budgetState, riskLevel, traceRefs, unresolvedDecisions, authorizedBy, controlReturnsWhen}`. Highest-leverage single change for multi-agent quality: today child issues get a description blob; a structured contract makes delegation lossless and lets the control plane *validate* handoffs (e.g., refuse a delegation whose budget state is exhausted).

### P3 — Layered failure taxonomy + deterministic validators over runs (O)
Adopt a MAST/AgentErrorTaxonomy-style coding of run failures by layer (E/T/C/L/O/V/G + model), applied automatically where deterministic: malformed tool calls, schema violations, JSON parse failures, 4xx-from-control-plane patterns, truncated commands. Paper evidence: **38% of production task failures were parsing errors fully addressable by deterministic checks**; root-cause isolation gives up to 26% relative success improvement. Concretely: a post-run classifier pipeline (rule-based inline → statistical drift → async LLM trace review) writing `failureAttribution` onto runs, aggregated per agent/adapter/skill in productivity reviews.

### P4 — Harness-change regression gates (V, Stage 5 + harness coupling)
Treat skills, agent instructions, adapter prompts, tool schemas, and permission policies as versioned harness components whose *changes trigger evals* — not just code CI. Minimum viable: a pinned suite of replayable rollout scenarios (we already have pinning tests for some skill text) that runs when `skills-releases/` or agent instruction docs change, reporting a success–cost–latency delta rather than pass/fail alone. Paper evidence: local harness improvements create global regressions because layers couple; "harness changes should be tested as system changes."

### P5 — KV-cache-aware prompt assembly discipline in adapters (C)
Audit adapter prompt construction against Manus's three rules: (1) stable prefix — anything volatile (timestamps, run ids, live wake payloads) goes *after* the stable system/skills prefix; (2) append-only turn history; (3) deterministic serialization — **we already know Postgres jsonb reorders keys; never serialize jsonb-round-tripped objects into prompts without canonical key ordering**. Also: don't mutate the delivered tool/skill set mid-session. Evidence: 10× cached-vs-uncached token price spread; cache hit rate as "the single most important metric" for production agents. This is measurable (log cache-hit rates per run) before/after.

### P6 — Approval liveness engineering (G + E)
Two moves. (a) Measure the **permission-prompt rate per run** as a first-class liveness metric; the paper is explicit that approval fatigue is a failure mode with hard data (17% attention / 3% comprehension). (b) Reduce it the way Anthropic did (84% reduction): widen default sandbox boundaries (filesystem/network allowlists per issue workspace) so in-bounds actions never prompt, and reserve interactions/approvals for genuinely consequential out-of-bounds actions. Design review for each approval surface: validation scope, alert richness, recurrence policy (allow-once vs allow-always per tool+args pattern).

### P7 — Declarative governance constitution (G)
Consolidate what is currently spread across agent instructions, experimental flags, adapter config, and code (tool allow/deny, budget limits, approval routing, risk tiers, audit destinations) into one versioned, diffable per-company policy document the control plane enforces. Board members can review policy PRs without reading TypeScript. Add consistency validation (no contradictory allow/deny; no uncovered tool categories). Paper evidence: deployment-time constitutions are auditable and updatable where training-time and code-embedded policy are not; no standard exists yet — early movers get to define it.

### P8 — Meta-monitoring & harness simplification (O + §12.5)
Instrument which harness interventions actually fire and change outcomes: watchdog recoveries, done-gate rejections, monitor wakes, compaction events, approval gates. Quarterly "harness pruning" review: interventions that never fire (or fire only for weaker models) are stale assumptions. Paper evidence: Anthropic deleted sprint constructs + context resets on a model upgrade and cut cost 37.5% with no quality loss. For Paperclip this also means per-model harness profiles — the scaffolding a Haiku-class coder needs is overhead for an Opus-class one.

### P9 — Collective memory with post-error recall (C)
Paperclip agent memories are per-agent; the same gotcha gets rediscovered by every agent (observable in our own memory files: multiple agents independently learning the same API pitfalls). Borrow cq's model: an org-tier shared knowledge store (local → team → company tiers) with a **post-error hook** — when a run hits an error, the harness queries collective knowledge before the agent retries blind. Our memory-file format (name/description/type frontmatter) is already compatible; the delta is a shared tier + automatic error-triggered recall injection.

### P10 — Trajectory-level judgement in reviews (V, Stage 4)
Done-gates and QA validate outcomes. Add trajectory checks to productivity reviews / watchdogs: redundant tool-call loops, permission-boundary probes, budget-burn anomalies, repeated-work detection (the signature of context drift). Per the paper, run these **async over the audit trail** (trajectory-level), keeping inline checks cheap. This is also our concrete defense against context drift, which the paper says cannot be solved in the C layer at all.

### P11 — Credential placeholder substitution (G)
Enforce the Skyvern pattern platform-wide: secrets resolve to placeholders in anything that enters model context (prompts, tool results, logs); raw values substituted only in the execution layer at invocation time. We already vault secrets and warn on exposure; the gap is systematic substitution + scrubbing on the tool-result return path (H3), and a renewal path for mid-run token expiry (our 1h run-JWT re-mint is a special case of this — generalize it).

### P12 — Evaluator-under-test (V, Stage 4)
Version and regression-test our graders: done-gate regexes, Greptile verdict parsing, QA rubric prompts, watchdog heuristics. A flaky grader silently misattributes noise to agents. Cheap start: when a gate/judge verdict is overturned by a human, record it as a grader-error datapoint; alert on grader error rates.

### Explicitly not borrowing (with reasons)
- **Graph engineering / LangGraph-style explicit workflow topologies**: the paper (and the article) warn against formalizing graphs before observing traces ("build a graph before understanding the work" is the #1 expensive mistake). Paperclip's issue-graph + blockers already *is* our workflow topology, discovered dynamically per task rather than frozen in a diagram. Keep control model-driven; revisit only for stable, high-volume pipelines.
- **microVM-per-run isolation**: our current threat model is prompt-injected-but-cooperative agents on our own infrastructure, which the paper says is exactly the case for OS-level permission boundaries rather than microVMs. Revisit when third-party/untrusted agent code runs on shared infra.
- **eBPF out-of-process monitoring**: right idea (unbypassable observation), wrong cost/benefit at our scale today; the audit-trail + trajectory-analysis route (P10) covers the need.
