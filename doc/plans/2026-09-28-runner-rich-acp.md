# Cursor, Copilot and Pi through rich ACP

Approved implementation plan, 2026-09-28. Shared base:
`c65fc9e3c81c41aafe421aa90a00514b84343285`.

Keep the existing ACPX runner transport and Codex app-server richness benchmark.
Implement a foundation prerequisite, then three separate provider branches and
PRs. Do not merge automatically. Preserve legacy Cursor/Pi adapters.

1. Investigate each pinned harness, its native API, ACP adapter, observed wire,
   runner normalization and UI surface. Inventory every meaningful event field.
2. Extend shared profile declarations, durable permissions/input, extension
   dispatch, steering/queue distinctions, artifact provenance and bounded display
   activity. Preserve existing replay and exact warm-session identities.
3. Pin complete provider distributions for macOS ARM64/x64 and Linux x64. Use
   verified launches, isolated credentials/configuration and build-time assets.
4. Implement Cursor native ACP and its question/plan/subagent extensions;
   Copilot ACP authentication/events/permission and settlement handling; Pi
   wrapper patch and owned extension with authenticated tools and input policy.
5. Run deterministic, recovery, isolation and richness conformance. Qualify each
   provider locally and in Daytona with product E2E evidence before advertising
   support. Use a combined $100 ceiling: $25 each plus $25 diagnosis reserve.
6. Run required full checks, prepare one foundation and three dependent PRs,
   retain evidence and deliver the comparative capability report. List every
   unused/partial capability with reason and prioritized follow-up.

Implementation and qualification status is maintained in
[the capability report](../architecture/runner-rich-acp-capabilities.md).
Missing credentials or spend verification leave qualification pending; they do
not authorize a weaker supported profile or an implicit model fallback.
