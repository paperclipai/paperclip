Each row is an issue that cannot legitimately be in this state: it is `blocked`, nothing
unresolved is blocking it, and the recovery action that was supposed to own it has already
closed. Nothing will re-fire on these — they sit until a human notices.

`blocks_n` = how many OTHER issues it is holding up; work the high ones first.
`loops`    = how many times an AGENT was dispatched at this issue (owner_type='agent' only).
             Board-escalated actions are excluded: past the cap of 3 (6e68b1eb8) the platform stops
             dispatching agents and hands the issue to the board, so counting those rows would
             report a correctly-escalated issue as still looping. >1 means re-dispatching
             it ALONE does not fix it — the lane exits without a disposition every time, so a
             plain bounce back to `todo` just re-enters the trap. Fix the exit, not the status.

REMEDY (per issue): confirm the work state, then give it a real disposition —
  - deliverable is finished  -> `done`
  - work remains             -> `todo`, so the assignee's normal pick-work path takes it
  - genuinely blocked        -> `blocked` WITH first-class `blockedByIssueIds`, never free text

⛔ THE LINE: this guard reports. It does not re-dispose issues, because choosing between
"finished" and "work remains" requires reading the actual deliverable. Route each one to its
assignee lane; do not guess on their behalf.
