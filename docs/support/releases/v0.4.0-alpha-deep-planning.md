## Post-RC-3 Committed Changes (RC-4)

The following changes landed after the RC-3 tag and are included in RC-4:

### C-1: LLM Trust Boundary — Zod Validation of Action Signals

**Commit**: `75c6c27a41`

The board-chat SSE action signal parser now validates LLM output against a strict Zod schema before emitting action events to the UI:

- **Allowed types**: `issue`, `plan`, `approval`, `knowledge`, `memory` (only known enums accepted)
- **Allowed actions**: `create`, `update`
- **URL restriction**: `data.url` must use `http:` or `https:` protocol only (no javascript:, data:, file:)
- **Length limits**: title ≤ 500 chars, id ≤ 200 chars, rationale ≤ 5000 chars
- **Max blocks**: at most **10 action blocks** per response — additional blocks are silently truncated with a server log warning
- **Silent skip**: blocks with unrecognized types, invalid actions, or failed validation are silently skipped (with server-side `console.warn`) — the conversation still persists normally

Previously only basic JSON parsing was applied. Now the full Zod schema provides a trust boundary ensuring only model output that matches the expected shape reaches the SSE stream.

### C-2: TOCTOU Safety Net — Post-Insert SLA Dedup Verification

**Commit**: `75c6c27a41`

The SLA monitor alert issue creation path now has a **post-insert duplicate verification** step. After INSERT, the server re-checks for a near-simultaneous duplicate. If one exists, the newer issue is hidden (cancelled), and a `## Duplicate SLA Alert Suppressed` comment is added to the original with a reference to the suppressed duplicate. The response returns the original issue enriched with `deduplicated: true` and reference fields.

Previously, two concurrent requests could both pass the pre-insert dedup check and create duplicate tracking issues for the same SLA breach.

### C-3: Search Safety — plainto_tsquery

**Commit**: `75c6c27a41`

Knowledge document search and memory warm-up now use `plainto_tsquery('english', query)` instead of hand-constructed `to_tsquery` strings. User queries containing punctuation, operators, or special characters are tokenized as natural language — special characters are stripped rather than causing PostgreSQL query errors.

Previously, searching for queries with special characters like `@`, `!`, or `#` could return a 500 error. See the [Search Safety KB article](../kb/search-safety-plainto-tsquery.md).

### Memory Extraction Jobs

**Commit**: `466c30fde7`

New API endpoints and UI for monitoring memory extraction jobs:

- `GET /companies/:cid/memory/extraction-jobs` — list jobs (newest first, with status/limit filters)
- `GET /companies/:cid/memory/extraction-jobs/:jobId` — get single job
- `POST /companies/:cid/memory/extraction-jobs/:jobId/retry` — retry a failed job
- The Memory Browser UI gains an **Extractions tab** with job status, source hyperlinks, and latency/cost display. The extraction jobs dashboard polls every 15s. Failed jobs can be retried with one click.

### Batch Gate Counts on Plan Cards

**Commit**: `466c30fde7`

Plan cards in the issues list and Plans page now show the count of active (non-superseded) review gates on each plan document. The `IssueDocument` type gains a `gatesCount?: number` field, populated from a batch-fetch of gate counts per (documentId, revisionId) pair. This eliminates the previous N+1 query pattern when rendering plan lists.

### Plan Gate Live Events

**Commit**: `466c30fde7`

The server now emits `plan.gate_created` live events when a review gate is created, in addition to the existing `plan.gate_resolved` event. The `LiveUpdatesProvider` dispatches both events, keeping the Plans page and issue detail in sync without polling.

### Board-Chat Regex Fix (Turn Tag Escaping)

**Commit**: `466c30fde7`

A regex capture group fix in `board-chat.ts` ensures turn tag escaping works correctly. Previously the non-capturing group `(?:...)` in the `serializeTurn` regex was incorrectly using a capturing group, which could leave some tags unescaped. Now uses a non-capturing group: `(<\/?turn\b)` → `/(<\/?turn\b)/gi`.

## Summary

This alpha release delivers **Deep Planning** — the first workstream of Project Polaris. Deep Planning replaces ad-hoc plan descriptions with structured, revisioned plan documents that carry sections, milestones, and approval gates. It enables agents to plan at a deeper level, get plans reviewed and approved gate-by-gate, and decompose approved plans into concrete child issues.

Also included in this alpha: the **Memory & Knowledge** foundation (pgvector-based agent memory and a knowledge document system), which ships alongside Deep Planning in the v0.4.0 line, and **Chat-to-Work Resolution** (Workstream C) — clickable resolution cards in the Conference Room chat when the board assistant creates or updates work objects.

## Highlights

### 1. Structured Plan Documents

Plans are now structured, revisioned documents attached to issues. Each plan has:

- **Sections** — Named blocks (Overview, Implementation Steps, Risks, etc.) with ordered display
- **Milestones** — Tracked checkpoints with status (`pending`, `in_progress`, `completed`, `cancelled`) and acceptance criteria
- **Revision history** — Every update creates a revision with change summaries and diff endpoints
- **Status** — `draft` → `in_review` → `approved` → `superseded`

**User value**: Plans are easier to read, navigate, and track. Teams can see exactly what changed between revisions and why.

### 2. Plan Review Gates

Agents can now create approval gates on plan revisions. Gates are linked to milestones and carry acceptance criteria:

- Create gates per plan revision
- Assign gates to specific agents
- Approve or reject with resolution comments
- When all gates for the current revision approve, the plan auto-transitions to `approved`

**User value**: Plans get explicit, auditable approval checkpoints. Nothing ships until the gates say it's ready.

### 3. Approved Plan Decomposition

Once a plan is approved, a plan confirmation is presented to the board. After a **board user accepts** the confirmation, agents can decompose the plan into child issues:

- Decomposition references the approved plan revision
- Child issues are created with the plan's milestones and structure
- The previous ad-hoc decomposition workflow is replaced
- **Human acceptance is required** — agents cannot accept the plan confirmation themselves; a board user must accept it via the board UI

**User value**: Plans turn into executable work directly, with a clear link back to the approved plan — and with a human decision point ensuring only board-confirmed plans become work.

### 4. Plan Board UI (New)

A new **Plans** page at `/plans` (sidebar, under Work) gives operators a complete plan management surface:

- **Browse plans** — List view with status badges, section count, and milestone progress indicators
- **Plan detail** — Structured sections rendered with markdown, milestone status, version info
- **Approval gate management** — See pending gates, approve/reject with comments, view gate history
- **Revision browser** — Browse revisions, select one to view inline diffs with added/removed/unchanged lines
- **Issue detail integration** — Plan sections, gates, and revision browser also mount inside the Issue Detail page when an issue has a plan document

### 5. Agent Memory (pgvector)

A durable, queryable agent memory system:

- **Memory bindings** — Company/agent configuration connecting to the built-in pgvector provider
- **Memory capture** — Auto-capture text with 30-day TTL
- **Memory records** — Curated, consciously saved entries with upsert
- **Hybrid query** — Semantic + full-text search
- **Scope isolation** — Agents see only their own memory; shared records visible company-wide
- **Audit log** — All memory operations logged

**User value**: Agents remember important context across runs, making long-horizon work more reliable.

### 6. Memory Browser UI (New)

A dedicated **Memory Browser** page at `/memory` (sidebar, under Work) lets operators inspect and manage agent memory:

- Browse records with cursor-based pagination
- Search via semantic + full-text hybrid query
- View record details (text, summary, scope, source, metadata)
- Filter records by metadata (JSONB containment)
- Forget individual records
- View recent memory operations audit log

### 7. Knowledge Documents

A full knowledge base within Paperclip:

- CRUD with lifecycle: `draft` → `in_review` → `published` → `archived`
- Revision history with diff endpoints
- Backlinks to issues
- Full-text search across published documents

**User value**: Teams can maintain a living knowledge base that agents search and reference during execution.

### 8. Knowledge Browser UI (New)

A dedicated **Knowledge Base** page at `/knowledge` (sidebar, under Work) gives operators a complete knowledge management surface:

- **Search** — Full-text search across published documents, with status filters (All statuses / draft / in_review / published / archived)
- **List** — Browse all knowledge documents with their lifecycle status
- **Detail sheet** — View document content, metadata, and summary
- **Revisions & diff** — Compare any two revisions side-by-side (old version → new version)
- **Backlinks** — See which issues reference the document
- **Create & edit** — Create new documents (title, summary, markdown body) and edit drafts with review comments

**User value**: Operators can search, review, and manage the company knowledge base without the API. The previous gap — knowledge documents existed server-side but had no management UI — is closed.

### 9. Knowledge Publish Stale-Approval Guard (VOY-1255)

Publishing a knowledge document now requires an approved review on the **latest** revision. An approval from a prior review cycle (before the document was edited and re-submitted) is rejected. This prevents publishing with stale approvals and ensures only current, freshly reviewed content goes live.

### 10. Latest Review Status Accuracy (VOY-1256)

The `latestReviewStatus` field on knowledge document listings now accurately reflects the most recent review — `pending`, `approved`, or `changes_requested` — regardless of outcome. Previously it only surfaced `approved` reviews, which could hide documents awaiting re-review.

### 11. Knowledge Search Route Fix (Critical Bug)

The `GET /knowledge/search` endpoint previously sat **after** the `/:documentId` route in the router, so Express matched the literal string `search` as a document ID — making the search endpoint unreachable. The search route now registers **before** the document-ID routes, so full-text knowledge search works from both the API and the new Knowledge Browser UI.

### 12. Manager-Chain Issue Permissions (Authorization Grant)

Managers can now comment on and mutate issues assigned to agents in their **reporting subtree** (direct and transitive reports). Previously the boundary decision denied peer-issue mutations before the manager-chain grant could be consulted, which meant a CTO or COO could not close, reassign, or unblock issues owned by their own team. This unblocks day-to-day management of team-owned work.

### 13. Chat-to-Work Resolution Cards (Workstream C)

The Board Chat / Conference Room (`/board-chat`) now renders **clickable resolution cards** when the board assistant creates or updates Paperclip work objects. Previously created objects were only mentioned in conversational text — now they appear as structured inline cards.

**When the assistant:**
- Creates an issue → blue "Issue" card with title and View link
- Updates a plan → purple "Plan" card with action label
- Approves/rejects a plan gate → green "Approval" card
- Creates a knowledge article → amber "Knowledge" card
- Captures a memory record → teal "Memory" card
- Records a decision → yellow "Decision" card with summary and rationale

The resolution cards work through a structured signal protocol: the board skill appends `%%ACTIONS%%{...}%%/ACTIONS%%` JSON blocks to model responses, the server parses them and emits typed SSE `action` events, and the UI renders ResolutionCard components. The raw markup is stripped from persisted comments — only the cards remain visible to users.

**User value**: Operators can see at a glance what the assistant created or changed, with direct links to the objects. Reduces scanning for links in conversational text.

## Support Notes

- Plans, memory, and knowledge are **alpha** features. Expect changes before v0.4.0 stable.
- Memory requires the pgvector PostgreSQL extension (migration 0129).
- Knowledge documents, once deleted, are permanently removed — no soft-delete.
- Memory capture has a 30-day TTL by default; curated records persist until forgotten.
- **Knowledge publishing** (VOY-1255): an approved review is required on the **latest** revision. A stale approval from a prior review cycle is rejected.
- **Knowledge search** (route fix): the `/knowledge/search` endpoint is now reachable — it previously 404'd because the `/:documentId` route shadowed the literal `search` path. If a knowledge search fails with a 404, verify you are running at least `f09cf3bc6e`.
- **Manager-chain issue permissions** (authorization grant): a manager may comment on and mutate issues assigned to any agent in their reporting subtree (direct and transitive reports). If a CTO/COO reports they cannot close or reassign a team member's issue, verify the assignee is actually within their reporting chain — the grant only applies within the subtree.
- **Memory scope queries**: the `scope` parameter must be valid JSON. Malformed JSON returns a `400 Bad Request` with `"Invalid scope query parameter: must be valid JSON"`.
- **Memory metadata filtering**: memory query and record list endpoints support a `metadata` parameter for JSONB containment filtering. This lets operators filter records by custom metadata key-value pairs.
- **Plan gate approvals (H-2 fix, VOY-1269)**: a plan only auto-transitions to `approved` when **all** gates for the current revision are approved — zero pending **and** zero rejected. A single rejected gate blocks approval even if every other gate passes. Resolve the rejection by creating a new plan revision with fresh gates. Gate resolution is also atomic (transactional), so concurrent approvals cannot race.
- **Plan acceptance flow**: Decomposing an approved plan into child issues requires a **human board user to accept the plan confirmation** (`request_confirmation` interaction targeting the approved plan revision). Agents cannot accept this — only board users can. If decomposition fails with `"acceptedPlanRevisionId must have an accepted plan confirmation"`, have a board user accept the confirmation via the board UI first. See the [Plan Documents API Reference](/docs/api/plans) for the full flow.

### Re-audit Follow-up: P0-2 data migration + P1-1 cache invalidation order

A Release Engineer re-audit (VOY-1368) found two gaps in the original hotfix, both fixed and Staff-Engineer-re-verified (VOY-1370):

- **P0-2 — pre-existing doc submit collision**: the initial `v0.4.0-alpha` deployment created documents WITH an initial revision (`version = 1`, `change_description = 'Initial version'`). After the revision-removal change, `submitForReview` inserts `version: doc.version` (= 1), which would violate the unique index `knowledge_document_revisions_doc_ver_unique_idx` for every pre-existing draft/archived doc. Migration `0136` now appends an idempotent `DELETE` that removes stale initial revisions for draft/archived documents before the hotfix logic applies.
- **P1-1 — promoteFromMemory cache invalidation order**: `promoteFromMemory()` called `invalidateKnowledgeSearchCache()` BEFORE the DB read + insert transaction, letting a concurrent search repopulate the cache with pre-mutation data. The invalidate call now runs AFTER the transaction commits, matching the other 7 mutation sites.

**Customer impact**: No customer-facing behavior changes. These are internal reliability and correctness fixes that ensure the system behaves as originally intended by the Phase 5 code review.

## Notification System: Multi-Channel Notifications

**Commits**: `b4526451aa`
**Issues**: VOY-1342, VOY-1364, VOY-1367

A multi-channel notification system ships — the code that was temporarily excluded from the initial v0.4.0-alpha deploy scope (see Post-Release Hotfix section above) is now fully included.

**How it works:** Board users receive notifications about events requiring their attention. Each notification type can be configured per channel with independent preferences.

**Notification types:**

| Type | Trigger | Default Email |
|------|---------|---------------|
| `review_requested` | Issue transitions to `in_review` | Off (in-app only) |
| `approval_needed` | Approval is created on an issue | Off (in-app only) |
| `work_completed` | Issue transitions to `done` | Off (in-app only) |
| `budget_threshold` | Budget soft/hard limit crossed | On |
| `execution_error` | Agent run fails or times out | Off (in-app only) |

**Channels:** `in_app` (board notification panel), `email` (branded HTML via SMTP), `webpush` (browser push API).

**Digest options:** Choose `instant`, `daily`, or `weekly` bundling per notification type × channel.

**Automatic triggers:** Notifications fire automatically when:
- An issue moves to `in_review` (`review_requested`)
- An issue is marked `done` (`work_completed`)
- An approval is created (`approval_needed`)
- A budget threshold is crossed (`budget_threshold`)
- An agent run terminates with an error (`execution_error`)

All auto-notifications are **fire-and-forget** — a notification dispatch failure never fails the triggering operation.

**Deduplication (B3 fix):** Execution error notifications are deduplicated by `runId`, ensuring at most one notification per failed run even if multiple code paths detect the error.

**Configuration:** Email requires `SMTP_HOST`, `SMTP_USER`, `SMTP_PASS`. Without SMTP, email notifications are gracefully skipped (in-app delivery still works). Push subscriptions require browser Push API support.

**New endpoints:**

| Endpoint | Description |
|----------|-------------|
| `GET /notification-preferences` | List notification preferences |
| `PUT /notification-preferences` | Batch update preferences |
| `GET /notifications` | List notifications (paginated) |
| `GET /notifications/unread-count` | Unread count |
| `POST /notifications/read-all` | Mark all read |
| `POST /notifications/:id/read` | Mark one read |
| `GET/POST/DELETE /push-subscriptions` | Manage push subscriptions |
| `POST /notifications/send` | Manual send (agent or board user) |
| `POST /notifications/digest` | Trigger digest send |

| Agent receives 403 on billing mutation | Low | Expected behavior. Only board users can create/update/cancel subscriptions, report usage, or sync invoices. |
| Email notifications not delivering (SMTP configured) | High | Check SMTP credentials and server connectivity. Verify SMTP_HOST, SMTP_USER, SMTP_PASS are set correctly. |
| Notification system causing request failures | Critical | Notifications are fire-and-forget — must never fail the triggering request. Escalate to CTO immediately if observed. |
| Billing webhook not processing events | High | Verify STRIPE_WEBHOOK_SECRET matches Stripe dashboard; check Stripe dashboard for failed webhook deliveries. |
